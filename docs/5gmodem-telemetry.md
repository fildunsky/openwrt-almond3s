# Метрики модема для Almond: источник — телеметрия 5gmodem

С 2.4.22 luci-app-5gmodem сам пишет каноническую телеметрию. Для Almond это
значит: **модемные метрики больше не собираем сами** — ни вызовов
`5gmodem.sh`, ни чтения его внутренних снимков `/tmp/5gmodem_metrics_*`.
Единственный поддерживаемый источник:

```
/tmp/5gmodem_tele.json
{"sig":64,"oper":"T-Mobile","rsrp":-99,"rsrq":-10,"sinr":1,"temp":42,"band":"B7","ca":"B3+B7","mode":"4G","ping":87,"rx":5865635,"tx":112640,"sms":0}
```

Обновляется тиком сторожа 5gmodem (каждые ~15–30 с), атомарно (tmp + mv) —
читать можно в любой момент, полуфайла не бывает. Поля и правила — по нашей же
схеме (`telemetry-schema.md`), 5gmodem ей следует строго.

## Правила чтения (обязательные)

1. **Отсутствие ключа = нет данных.** Не подставлять 0/-1; на экране — прочерк,
   в TLV — поле не передавать, в MQTT — ключа нет.
2. **Свежесть по mtime файла.** Файл старше ~90 секунд → экспортёр 5gmodem не
   работает (пакет удалён/сторож остановлен) — вся модемная карточка
   недоступна. Файл свежий, но без модемных полей (остался, например, только
   `sms`) → модем вынут или интерфейс лежит: это штатное состояние, показывать
   «модема нет», а не последние значения.
3. **Не кэшировать поверх.** Прочитал — показал; свои «липкие» последние
   значения не хранить, 5gmodem уже отвечает за честность файла.

## Разделение ролей

| Кто | Пишет | Куда |
|---|---|---|
| 5gmodem | `sig oper rsrp rsrq sinr band ca mode temp ping rx tx sms` | `/tmp/5gmodem_tele.json` |
| Агрегатор Almond | `batt chg cpu mem disk up wifi vpn vpn_node` | `/tmp/almond_tele.json` (или свой существующий) |

Каждый пишет только своё. Потребитель (экран, Zigbee, MQTT) **мержит оба
файла** при отправке; при коллизии ключей модемные поля берутся из 5gmodem.

**Публикатор MQTT должен быть один.** На Almond им остаётся наш агрегатор
(он уже знает batt/cpu и публикует объединённое состояние). У 5gmodem есть
собственный MQTT-паблишер — на Almond его НЕ настраивать (не задавать
`5gmodem.tele.mqtt_host`), иначе в Home Assistant появятся два устройства с
пересекающимися сенсорами.

## Чек-лист сверки (пройти по коду и отчитаться по пунктам)

- [ ] LCD-страницы (ui.uc и виджеты) читают модемные метрики из
      `/tmp/5gmodem_tele.json`, прямые вызовы 5gmodem-скриптов удалены.
- [ ] Zigbee-мост (`almond3s-zig.c`, массив `TELE`): маппинг полей сверен со
      схемой; для нового поля `ca` (строка) выделен идентификатор — занятые
      сейчас 0x01..0x10, свериться, что таблица не разъехалась с числом полей.
- [ ] Правило «нет ключа = нет данных» соблюдено во всех трёх потребителях
      (экран, TLV, MQTT).
- [ ] Проверка свежести по mtime реализована; поведение «модем вынут»
      показано на экране осмысленно.
- [ ] MQTT публикует объединённый JSON (мерж двух файлов) одной темой
      состояния; discovery-темы — от одного устройства, без дублей с 5gmodem.
- [ ] Системная телеметрия Almond пишется своим файлом по тем же правилам
      схемы (атомарность, отсутствие ключей, округления).
- [ ] Частота чтения: не чаще раза в секунду (файл всё равно обновляется раз
      в 15–30 с; экрану достаточно читать раз в 2–5 с).

## Детали соты: ВЫПОЛНЕНО, читать из отдельного файла

Поля раздела 2.1 (`pci earfcn enb cid tac apn wan_ip modem nbrs`) 5gmodem
отдаёт — но НЕ в основном файле, а приложением:

```
/tmp/5gmodem_tele_cell.json
{"pci":432,"earfcn":3048,"enb":365392,"cid":93540375,"tac":33611,"apn":"internet","wan_ip":"100.81.154.210","modem":"Quectel EC21"}
```

Почему отдельно: основной файл — публикуемый (MQTT-состояние целиком,
HTTP-рецепт из инструкции), и 5gmodem обещает, что в нём нет ничего
локализующего. Детали соты (cid/tac/enb) и wan_ip — ровно такое. Ограничения
из раздела 2.1 при этом выполняются сами собой: файл-приложение никем не
публикуется, читает его только экран.

Дополнение 20.08.2026: в файле-приложении теперь ВЕСЬ набор страницы —
`mcc mnc lac cid_hex bandwidth pathloss txpower cqi uecat volte mimo rxdiv
antports csq rssi conn_time therm simslot roaming fw phone nca` и несущие
`s1..s4` (band/pci/earfcn/rsrp/rsrq/sinr/state). Прямой вызов можно убирать.
Нюансы: `mnc` — СТРОКА (ведущий ноль значащий: «02» у МегаФона); `phone`
допущен только в этом локальном файле — решение зафиксировано в схеме;
витринные строки (bandwidth «20 MHz», txpower, mimo, antports) — как в
снимке, показывать как есть; поля, которых модем не отдаёт, отсутствуют.

Коллектору: заменить чтение этих полей на `/tmp/5gmodem_tele_cell.json`
(правила те же — атомарный, «нет ключа = нет данных», свежесть по mtime) и
убрать последний прямой вызов. В `nbrs` объекты могут нести больше ключей,
чем в примере схемы (`earfcn`, `rssi`, `serving`) — лишние игнорировать,
`serving:1` можно использовать для подсветки обслуживающей соты.

## Ответ на вопрос про обрезанный файл (20.08.2026)

Причина найдена на стороне 5gmodem: сборщик метрик публикует снимок и с
пустым сигнальным ядром, когда AT-порт в момент сбора занят другой операцией
(странице это не мешает - она рисует прочерки, а телеметрия честно выкидывала
пустые ключи). Исправлено по предложенному правилу: осечка опроса больше НЕ
публикуется - если новый снимок свежий, но без ядра (ни sig, ни rsrp, ни
oper), а прежний файл ядро содержал, экспортёр оставляет прежние файлы
нетронутыми. Настоящее «модем вынут» сигнализируется протуханием источника
(файл без модемных полей появляется только через TTL), так что контракт
«свежий файл без полей = модема нет» снова строгий.

Твой запас в три пустых чтения можно оставить как ремень безопасности - он
теперь сработает разве что на самом переходе TTL. Расширенный признак наличия
модема (sig ИЛИ rsrp ИЛИ oper) - правильный, оставляй.

## Отладка на живом устройстве

```sh
cat /tmp/5gmodem_tele.json                  # что отдаёт 5gmodem
/usr/share/5gmodem/telemetry.sh write       # пересобрать прямо сейчас
date -r /tmp/5gmodem_tele.json              # свежесть
```

Полная инструкция потребителя (все способы забора, MQTT/HA, HTTP) — в репо
5gmodem: `docs/telemetry.md`.
